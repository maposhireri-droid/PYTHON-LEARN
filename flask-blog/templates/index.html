Writing the code turned out to be the easy part. Getting it in front of the internet was its own education. Copy-paste broke between apps on my phone, so I uploaded files one at a time through GitHub's browser editor — which flattened my folder structure and left templates/ and static/ as loose files instead of real folders. The app deployed fine on Render, then immediately died with jinja2.exceptions.TemplateNotFound.

Fixing it meant learning tools I'd never touched: installing Termux to get a real Linux terminal on Android, generating a GitHub personal access token because passwords don't work over HTTPS anymore, and finally running git add, git commit, and git push from an actual command line instead of a web uploader. Even after the folder structure was fixed, the site still 500'd — turned out Render's Root Directory setting was blank, so it was building from the repo root instead of the flask-blog subfolder the whole time.

None of this was in a tutorial. It was reading logs, matching error messages to causes, and fixing one wrong assumption at a time — which, it turns out, is most of what shipping software actually is.

7e2c9d4 tag: week-10

feat: encapsulation, inheritance, polymorphism, abstraction

expand ▾
Author: Keirano <learning@self> · OOP pillars

This is where OOP stopped being one idea and became four distinct ones. I started with a Wallet class and made its balance private using a double underscore — self.__balance — which Python enforces by "name mangling" the attribute so it can't be touched directly from outside the class. Trying to print account.__balance throws an AttributeError. To read it safely, you write a get_balance method instead — the object controls access to its own data rather than handing it out freely.

@property is the cleaner version of that same idea. Instead of calling get_radius() like a method, a getter decorated with @property lets you read my_circle.radius like a plain attribute, while still running code behind the scenes. A matching @radius.setter lets you write to it the same way, but with validation — mine raises a ValueError if someone tries to set a negative radius. The trap I nearly fell into: inside the setter, you can't assign to self.radius again, or it calls itself forever. You assign to the underlying private attribute, self._radius, instead.

Inheritance let a Dog class reuse everything from an Animal class while overriding just the parts that differ, and super() let me call the parent's version of a method and build on top of it rather than replacing it outright. Polymorphism was the payoff for that: a Cat, a Dog, and a Monkey can all define their own speak(), and I can loop over a list of them calling animal.speak() without caring which one it is — same method name, different behavior per class.

Abstraction tied it together conceptually. Using Python's ABC and @abstractmethod, I can define a class like TalkingToy that cannot be instantiated on its own — it only exists to guarantee that any subclass (RobotToy, TeddyBearToy, DinosaurToy) implements a speak() method in its own way. As my own comment put it: abstraction is about focusing on what something does, not how it does it.
